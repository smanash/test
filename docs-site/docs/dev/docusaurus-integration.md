This page documents **how** `flexday-ai-user-manual.html` became this Docusaurus site, so anyone
picking this up later doesn't have to reverse-engineer it. It is not part of the user-facing
manual — it's dev documentation about the site itself.

> **This file is NOT touched by `npm run convert`** (the migration script wipes and regenerates
> everything else under `docs/`, but deliberately leaves `docs/dev/` alone — see
> "Re-running the migration" below). If you ever see this file missing after running the script,
> that's why: it was never supposed to be regenerated, only hand-maintained.

## Why Docusaurus

The source manual (`flexday-ai-user-manual.html`, copied into `source/` in this project — see
below) is a single hand-styled, print-oriented HTML file — good for a PDF/print artifact, bad as a
living website: no navigation between sections beyond a table of contents, no search, no
versioning, and every edit meant hand-editing raw HTML + embedded CSS. Docusaurus (open-source,
React-based, static-site generator built for documentation) gives this content for free:

- A sidebar + prev/next navigation generated from simple Markdown files.
- Full-text search (once `@docusaurus/theme-search-algolia` or the local search plugin is wired
  up — not done yet, see [Known limitations](#known-limitations) below).
- Light/dark mode, responsive layout, and a stable URL per section — none of which the original
  print HTML had.
- Content that a non-engineer can edit: each Part is a plain Markdown file with a few
  Docusaurus-specific conventions (admonitions, image syntax) instead of raw HTML/CSS.

## Project layout

This is `docs-site/` — a project inside the `flexday-ai-studio` monorepo, alongside `studio-api`,
`studio-ui`, `admin-ui`, and `solutions-app`. It is deliberately **not** in
`scripts/gate.sh`'s project table (the same treatment `dev_tooling/` gets, per CLAUDE.md): it
ships no application code, only converted manual content, so `npm run typecheck`/`lint`/`test` at
the repo root never touch it, and `test/unit/config/root-gate-wiring.test.ts` (which derives its
expected project set from CI's own path-scoping list) is unaffected by its presence.

```
docs-site/
  docs/                       the manual's content, one Markdown file per Part + glossary.md
    intro.md                    the site's home page (route "/")
    part1-getting-started.md    ... through part9-reference.md
    glossary.md                 every defined term, alphabetical
    dev/
      docusaurus-integration.md   this file — NOT regenerated by the conversion script
  source/                     the migration's input, copied in once for reproducibility
    flexday-ai-user-manual.html  the original hand-authored HTML manual
    manual-images/               its screenshots
  scripts/
    convert-manual.cjs         the HTML -> Markdown migration script (see below)
  static/img/manual/            the manual's screenshots, copied verbatim from source/manual-images/
  src/css/custom.css            Docusaurus theme overrides (currently just the scaffold default)
  Dockerfile                   builds the static site, then serves it with caddy:2-alpine
  docusaurus.config.js          site config — docs-only mode, no blog (see below)
  sidebars.js                   sidebar order (autogenerated from each file's sidebar_position)
```

## How the content was migrated

`scripts/convert-manual.cjs` is a **one-shot, re-runnable** Node script (`npm run convert`) that
reads `source/flexday-ai-user-manual.html` and regenerates everything under `docs/` (except
`docs/dev/`) and `static/img/manual/`. It does **not** feed the whole HTML document through a
generic HTML→Markdown converter — the source manual's custom markup (definition boxes, callout
notes, annotated screenshots, "where am I" path badges) carries meaning a generic converter would
flatten. Instead it walks the document's actual structure (`cheerio`, a jQuery-like HTML parser)
and only hands small, already-understood fragments to
[Turndown](https://github.com/mixmark-io/turndown) (an HTML→Markdown converter) for the generic
stuff — plain paragraphs, lists, tables, bold/italic/code.

Mapping from the source manual to this site:

| Source HTML | Becomes |
|---|---|
| `<div class="part" id="p1">` (one of nine) | `docs/part1-getting-started.md` (one file per Part, in Part order) |
| `<section class="sec"><h3>1.1 …</h3>…</section>` | A `##` heading + its content, inside that Part's file |
| `<div class="defs"><p class="define" id="g-x"><b>Term</b> desc</p></div>` | **Two places**: (1) a `:::note Terms on this page` admonition inline, where the term is introduced, and (2) one entry on the standalone `docs/glossary.md` page (deduplicated — a term defined once in the source is written once here, even though the source repeats the glossary link many times) |
| `<div class="note tip/warn/stop">` | A Docusaurus admonition: `tip` → `:::tip`, `warn` → `:::warning`, `stop` → `:::danger` |
| `<figure><img><figcaption>…</figcaption></figure>` | A Markdown image + an italic caption line + (if the figure had a numbered legend) a bullet list of legend items |
| `<span class="where">/t/&lt;workspace&gt;</span>` | An inline-code blockquote line, e.g. `` > `/t/<workspace>` `` — rendered as code so the literal `<workspace>` is never mistaken for an HTML/JSX tag by MDX (see [MDX gotchas](#mdx-gotchas)) |
| `<a class="gloss" href="#g-x">term</a>` | `[term](/glossary#slug)`, where `slug` is computed with the same slugger Docusaurus uses internally for heading anchors (see below), so a glossary link can never point at an anchor that doesn't exist |
| `<kbd>Ctrl</kbd>` | `` `Ctrl` `` (inline code, to keep the "looks like a physical key" styling without embedding raw HTML) |
| `manual-images/*.png` | Copied into `static/img/manual/`, referenced as `/img/manual/*.png` |

### MDX gotchas

Docusaurus compiles every `.md`/`.mdx` file as **MDX** (Markdown + embedded JSX), which means a
literal `<` or `{` in prose text is normally parsed as the start of an HTML tag or a JS
expression — not as a plain character. The source manual's `&lt;workspace&gt;` placeholders
(e.g. `/t/<workspace>`) decode to real `<`/`>` characters once parsed out of the HTML, so
rendering them as plain prose would break the MDX build. The script handles this two ways:

1. Anywhere the source **already** intends "this is a literal path", it's rendered as inline code
   (`` `/t/<workspace>` ``) — MDX does not parse the contents of a code span as JSX/expressions,
   so this is both correct-looking *and* safe.
2. As a backstop, any other stray `<`, `>`, `{`, `}` reaching plain text is escaped to its HTML
   entity form before being written out (see `mdEscapeText` in the script). This never fired for
   the actual manual content — every `<...>` in the source turned out to live inside a `.where`
   span, which is caught by rule 1 — but it's there so a **future edit to the source HTML** can't
   silently reintroduce a build break.

A second MDX gotcha, hit and fixed during this migration: Docusaurus's documented
`## Heading {#custom-id}` syntax (giving a heading an explicit anchor) failed to compile
(`Could not parse expression with acorn`) against the MDX version pinned by this Docusaurus
release. Rather than fight that, the glossary page uses **plain headings** (`### Term`, no
`{#id}`) and the script computes each term's anchor itself with `github-slugger` — the exact
slugging library Docusaurus uses internally to auto-generate heading anchors — in the same
top-to-bottom, alphabetically-sorted order the glossary page renders in. That's why the script
does a first pass to build an `id -> slug` map *before* rendering any Part page: every inline
`[term](/glossary#slug)` link has to agree with the anchor Docusaurus will actually assign to
that heading.

### Re-running the migration

If `source/flexday-ai-user-manual.html` is edited (content, not just a typo — for a genuine
content change), regenerate the site from it rather than hand-editing the generated `docs/*.md`
files, or the two will drift:

```bash
cd docs-site
npm run convert
```

This **overwrites `docs/` entirely except `docs/dev/`** and re-copies every image into
`static/img/manual/`. It is idempotent — running it twice in a row produces byte-identical output.

If instead you want to **hand-edit the manual going forward** (skip the HTML source entirely and
edit Markdown directly), that's a supported path too — just stop running the script, and treat
`docs/*.md` as the source of truth from then on. The two workflows shouldn't be mixed for the same
file: an edit made in `docs/part4-your-data.md` will be silently discarded the next time
`npm run convert` runs.

## Site configuration

- **Docs-only mode**: the blog plugin is disabled (`blog: false`) and the docs plugin is mounted
  at the site root (`routeBasePath: '/'`), because the entire site *is* the manual — there's no
  separate marketing homepage or blog. `docs/intro.md` carries `slug: /` and is the site's actual
  home page.
- **Sidebar**: `sidebars.js` uses Docusaurus's `autogenerated` sidebar type over the `docs/`
  folder, ordered by each file's `sidebar_position` frontmatter (`0` for the intro, `1`-`9` for
  the Parts in order, `99` for the glossary, `100` for this dev page). The conversion script
  stamps these automatically, so the sidebar never needs manual reordering when the manual is
  regenerated.
- **Broken-link checking is strict**: `onBrokenLinks`, `onBrokenAnchors`, and
  `onBrokenMarkdownLinks` are all set to `'throw'` in `docusaurus.config.js`, so `npm run build`
  fails loudly if a glossary link, an image path, or a cross-Part link ever points at something
  that doesn't exist — which is exactly what caught the two MDX issues above during this
  migration, before they could ship silently.

## Editing on GitHub (the everyday path)

Every page carries an **✏️ Edit this page** link at the bottom, pointing at that file in
GitHub's web editor on `develop` (`editUrl` in `docusaurus.config.js`). The full loop needs no
local checkout:

```
Open the page  →  ✏️ Edit this page  →  edit in the browser  →  Commit changes
      →  GitHub opens a PR (develop is protected)  →  CI runs `docusaurus build`
      →  merge  →  docs-site-deploy.yml rebuilds + deploys  →  live manual updated
```

Two guards sit in that loop deliberately, because the person editing has no way to run a build
themselves:

- **`docs-site` job** in `.github/workflows/flexday-dev-ci-checks.yml` — runs
  `docusaurus build` on the PR. Since `onBrokenLinks` and `onBrokenAnchors` are `throw`, a
  mistyped link or a deleted page someone still references fails the check rather than
  producing a live 404.
- **`docker` job** — validates `docs-site/Dockerfile` still builds, so a deploy is never the
  first time the image is assembled.

`.github/workflows/docs-site-deploy.yml` is the deploy half. It is path-scoped to
`docs-site/**`, ships **only** that folder to the VM (a docs edit structurally cannot alter
`studio-api`, the compose files or the `Caddyfile`), and rebuilds that one container. It
**skips its own deploy step, with a notice, until `DOCS_DEPLOY_SSH_KEY` and
`DOCS_DEPLOY_HOST` exist as repository secrets** — so it is safe to merge before the VM side
is wired, and turning it on later is adding secrets rather than editing the workflow.

## Running it locally

```bash
cd docs-site
npm install        # first time only
npm start          # dev server with hot reload, default http://localhost:3000
npm run build      # production static build -> build/
npm run serve      # serve that production build locally (no hot reload)
```

Pick whatever port is convenient (`npm start -- --port 3300`, say) if `3000` collides with
`studio-ui`'s own local dev server.

## Deploying it

This site is wired into the main `flexday-ai-studio` deployment as its own container —
see `docs/deployment.md`'s **"The user manual (`docs-site`)"** section in the repo root for the
operator-facing steps (DNS, bringing the container up, verifying). The short version:

- `Dockerfile` is a two-stage build: a `node:24-bookworm-slim` stage runs `npm run build`
  (`docusaurus build`, which needs no live source repo or database — it's fully static), and the
  runtime stage is just `caddy:2-alpine` serving the resulting `build/` folder. There is
  **no Node process at runtime** — once built, this is plain static HTML/CSS/JS.
- `docusaurus.config.js`'s `url` is read from the `DOCS_SITE_URL` build ARG (mirroring the
  `NEXT_PUBLIC_*` build-arg pattern the Next.js apps use, minus that prefix since nothing here
  ships into a client bundle that reads `process.env` — it only shapes the sitemap/canonical-URL
  metadata Docusaurus bakes into the static HTML).
- It needs **no CORS entry, no auth, no shared volume, and no database** — it never calls
  `api.<DOMAIN>` or any other service. That's also why it's the simplest service in the whole
  compose file.

## Known limitations

Things deliberately **not** carried over from the original HTML/print design, and not yet added:

- **No search.** Docusaurus ships local search via a community plugin
  (`@easyops-cn/docusaurus-search-local`) or hosted via Algolia DocSearch; neither is wired up
  yet. For a manual this size, local search is the simpler first step.
- **The cover page's design (logo, "Classification: Public" band, version table) was not
  recreated.** Docusaurus has its own visual language (navbar + sidebar + content), and
  reproducing a print cover page inside it would fight that rather than use it. The site's
  navbar/footer currently use the scaffolded default Docusaurus logo/favicon
  (`static/img/logo.svg`, `static/img/favicon.ico`) — swap those for Flexday's real logo/favicon
  when convenient.
- **Screenshot callout markers** (the numbered circles/boxes the source HTML drew *on top of*
  some screenshots via absolutely-positioned `<span class="call">` overlays, keyed to a legend
  below the image) are **not reproduced as overlays** — the legend text survives (as a bullet list
  under the image caption), but the numbered markers themselves don't appear on the image. Doing
  this properly would mean either baking the markers into the PNGs themselves (a one-time image
  edit) or building a small React component that lays them out over the image by percentage
  coordinates (the original stored `left/top/width/height` as percentages, which is recoverable
  from the source HTML if this is worth doing later).
