# Dhub proof of concept

A throwaway Docusaurus site used to evaluate **[Dhub](https://dhub.dev)** — a Git-backed visual
CMS — as a way of letting non-developers maintain documentation.

> **The content is the Flexday AI Studio user manual**, whose own cover page states
> `Classification: Public`. This repository is public, so the manual is world-readable and
> search-indexable under a personal account. Make the repository private if that is not wanted —
> nothing in the POC depends on it being public.

## What this POC is proving

1. A person with **no GitHub account** can edit documentation in a visual editor.
2. Their changes arrive as an **ordinary pull request**.
3. **Engineering keeps control** — the `main` branch requires a pull request, so a writer can
   propose anything and merge nothing.

## Why it mirrors a monorepo

The Docusaurus site deliberately lives in a **subfolder** (`docs-site/`) rather than at the
repository root, because the real project it is standing in for does the same. That makes the
"project directory" setting in Dhub's import dialog a real part of the test rather than a detail
that happens to be irrelevant here.

## Layout

```
docs-site/                    the Docusaurus site
  docs/
    intro.md                  headings · :::tip · link table
    getting-started.md        steps · :::note/:::danger · images · <kbd> · tables
    working-with-data.md      :::note/:::warning/:::danger/:::tip · JSON + SQL code · images
    troubleshooting.md        wide reference table · text code block
    glossary.md               ### headings used as anchor targets
  static/img/                 images referenced by the pages
  docusaurus.config.js        title, navbar, footer, editUrl → this repo
  sidebars.js                 autogenerated from docs/ + sidebar_position
```

Between them the five pages cover **all four admonition types**, tables, images with captions,
three code-block languages, inline code, `<kbd>`, ordered and unordered lists, cross-page links
and one anchor link (`/docs/glossary#workspace`).

## Running it locally

```bash
cd docs-site
npm install
npm start        # http://localhost:3000
npm run build    # production build + strict link checking
```

`onBrokenLinks` and `onBrokenAnchors` are both set to `throw`, so `npm run build` fails on a
broken link. That is the same guard the real project uses, and it is what makes a CMS safe to put
in front of non-technical writers: they cannot ship a link to a page that does not exist.

## Branches

| Branch | Purpose |
|---|---|
| `main` | **The single branch this POC uses.** Protected: Dhub connects here, and changes arrive by pull request |

The real project this stands in for uses a separate `develop` integration branch. A POC does not
need two, and a second branch is one more thing to keep in step for no benefit.

## The round-trip test

The point of the exercise. In Dhub's editor, confirm:

1. `:::tip` renders as a styled callout box, not as literal `:::tip` text
2. Tables render as tables
3. Images appear
4. Code blocks keep their syntax highlighting
5. **Edit a page → push it as a PR → pull it back → check nothing above was silently rewritten**

Step 5 is the one people skip. A CMS that renders correctly but *rewrites on save* will reformat
an entire manual on the first edit, and you find out in a pull request with hundreds of changed
lines.
